# 节点状态新鲜度准入分析

## 我的判断

这份数据包含 990 条作业执行记录：954 条有最终结果，其中 866 条成功、88 条异常中断；另有 36 条 `execution_ok` 为空。缺失结果不能直接记作失败，因此所有成功率和策略评估都只使用 954 条已回传记录。

主要信号是调度时使用的节点状态陈旧度，而非单纯资源水平。将 `submitted_at` 与 `node_synced_at` 统一解析为带时区时间戳后相减：状态年龄不超过 30 分钟的已回传作业成功率为 94.5%（769/814）；超过 30 分钟的成功率为 69.3%（97/140）。30 分钟以上组失败率约 30.7%，短龄组约 5.5%。可用内存和 CPU 与结果有较弱的单变量相关性（分别约 0.10、-0.07），不能据此断言它们无关，但在该数据中没有比同步年龄更强的单一信号。

**根问题判断：调度器可能在节点状态过期时仍将作业派发，导致准入依据与实际节点状态脱节。** CSV 只有观测关系，没有中断原因、节点状态变更时间或硬件实际状态，故这是高优先级待验证假设，不是因果结论。年龄分布中位数为 8 分钟，95 分位为 54 分钟，最大 65 分钟。

## 做了什么

- 提供 `analyze.py`，从原始 CSV 重算状态年龄、结果分布、训练/验证切分与门槛策略估算。
- 建议试行**15 分钟状态新鲜度门禁**：若 `submitted_at - node_synced_at > 15 分钟`，暂缓派发，触发节点状态刷新；刷新成功后重新准入，超时则转人工/告警。上线时应使用调度器当前时间对节点同步时间计算年龄，并记录准入判定和后续结果。
- 15 分钟不是通用硬件容量阈值，只是本样本上的初始候选。上线先影子运行并分区观察；按周复核失败率、拦截比例、刷新耗时和误拦截率，再调整阈值。还应检查未来时间戳、时钟偏差及空同步时间，并对缺失结果保持独立状态。

## 怎么证明有用

将有结果记录按 `submitted_at` 排序，前 70% 用于扫描候选阈值，后 30% 作为时间后置验证集。扫描 0–65 分钟、每 5 分钟一步，以题目给定代价最大化估算净工时：每命中一次失败避免损失 120 工时，每次拦截等待成本 12 工时。训练段选出的门槛为 15 分钟。

在后 287 条验证记录中，基线有 27 次失败（失败率 9.4%）。15 分钟门禁会暂缓 57 条：其中 19 条最终失败、38 条最终成功；若假设失败都能被避免且每次暂缓仅花 12 工时，则估算净节省为 `19 × 120 − 57 × 12 = 1,596` 工时。其余立即放行的 230 条中有 8 次失败，失败率 3.5%。这显示该门禁值得受控试点，但不是实际节省承诺：等待后失败是否真的被避免、暂缓耗时是否恒为 12 小时，数据都无法验证；它也可能增加排队延迟。因此生产实验需与对照组比较实际失败、等待工时和总交付时间。

验证集上，30 分钟门槛净估算 744 工时，15 分钟在本代价模型下更优。门槛是通过训练段选择，避免在同一批记录上挑选并报告最好结果。样本只有 287 条验证记录，结论仍有抽样不确定性，建议持续积累数据并分区复核。

### 复现

要求 Python 3 和 pandas（脚本在 pandas 2.2.2 下运行）：

```bash
python -m pip install pandas
python analyze.py
```

脚本只读取仓库根目录提供的 `job_executions.csv`，不使用补造数据。时间戳保留时区后计算分钟差；缺失结果从策略计算中排除。脚本将打印完整阈值扫描、所选门槛及验证集和全量观察数据估算。全量数据数字仅作描述性参考，不能视作独立验证。

## 数据与限制

唯一结论数据源是本题发放的 `job_executions.csv`，共 990 行。没有外部数据或自造数据。现有字段不含失败原因、需求内存/显存、节点容量基线、排队时长、重试结果和节点状态真实变更，因此无法推断资源准入阈值、失败因果关系或门禁的真实业务 ROI。建议先做影子模式，再做有回滚能力的小流量对照实验。
